# AGENTS.md — ADHD VN Reader

Instructions for AI coding agents working in this project. Read this before doing anything.

## What this project is

A Windows desktop app (Godot 4.7, GDScript) that turns text documents (.txt, .md, .docx, later PDF) into a visual-novel-style reading experience for people with ADHD: sentences appear one at a time in a VN textbox as if spoken by a character sprite, with backgrounds/sprites changing every N slides or randomly to keep the reader visually engaged.

**The owner is not a programmer.** The agent writes all code and explains results in plain language: lead with what changed and what to click to check it, and translate any jargon. The owner wants basics that work, not anything fancy.

## Vague requests are expected — follow this protocol

The owner often gives short, vague prompts ("fix the text", "make it nicer", "add the thing"). Handle them in this order:

1. **Infer from context.** Use the roadmap + current state below to figure out the most likely intent. State your interpretation in one line ("I'm reading this as X — tell me if you meant Y") and proceed.
2. **Ask when it matters.** If the answer would genuinely change what gets built (scope, behavior, or look — not trivia), STOP and ask before building. Ask in one batch: short numbered questions with 2–4 plain-language options each. Never fire a list of open-ended essay questions.
3. **Never stall on trivia.** If a choice is small or easily changed later (a label, a color, a speed value), pick a sensible default and mention it in one line.

Working styles the owner has enabled (these persist across sessions):

- **ponytail** (minimal code): fewest files, no speculative abstractions, mark deliberate shortcuts with `# ponytail:` comments, never rebuild what already works.
- **antislop** (UI honesty): no fake "final" assets, every control does something real, verify before delivering. Visual direction comes from the owner's brief: colorful, visually stimulating, but text stays readable.

- **Slide length caps (2026-10-08, late):** `TextParser.MAX_SLIDE_CHARS` (220). Three rules, and one hard lesson. (a) `_split_into_sentences` treats a terminator (`.` `!` `?` `…`) + optional closing quote followed **immediately** by an em/en dash as a sentence end and consumes the dash — pre-fix this is what rendered 19th-century chapter topic-lists (pg79737 *Myself and Others*, Jessie Millward, Ch. I: `I!—Henry Irving and my mother.—My father, Charles Millward.—…`) as single 231- and 476-char slides, worst in book 856. (b) `_is_initial()` stops `E. A. Sothern.` / `M. J. Whitty.` fragmenting into 2-char slides, which rule (a) would otherwise cause. (c) The grouping loop in `parse_string` flushes **before** appending (it used to check after, so a slide could overshoot by a whole sentence → 430 chars). **DO NOT re-add a comma/space force-cut.** The first attempt (`_break_long`, since removed) cut over-long sentences at the last break char before 220 including `,` and ` `, and it produced slides ending `...the nightmares had lashed at me for two weeks, and` — the owner flagged incomplete sentences as the exact thing to avoid. `_break_at_clause` now splits ONLY at `;` or `:` (author-written clause boundaries): the last one inside the window, else the **first one past it** (a 700-char sentence whose only `;` sits at char 250 must still be cut), else the sentence stays whole. Result on pg79737: 3,114 → 3,756 slides, longest 856 → 641, over-400 40, median 121. The 641-char remainder has no `;`/`:` at all and is left whole on purpose — shrink-to-fit (floor `max(14, 0.6*font_size)` in a `textbox_height` 260 box) absorbs it, so never "fix" it by cutting. Residual slides ending on a comma/dash are the BOOK's own text (poem lines, letter headers, Victorian `:—` speech markers), not parser cuts — the three split rules can only end a slide at `.!?…`, `;` or `:`. Regression tests: `test_verification.gd` 1f (topic list, initials, semicolon split, no-boundary sentence stays whole, "no slide ends mid-clause", grouping cap).
